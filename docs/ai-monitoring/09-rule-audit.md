# 09 — Rise Rule Audit (line-by-line, 2026-10-30)

Scope: the eight Rise rules in `rise-ai-monitoring/src/main/java/com/riseai/monitoring/rise/rule/`, plus `RiseEnvelope`, `RiseFindingEngine` and `RiseProjectionRepository`, which feed them. Method: each rule was read in full, its inputs and decision points traced, and every boundary, malformed-input, ordering and replay behaviour pinned by a test in `RiseRuleAuditTest` (21 tests) or in `RiseMonitoringIntegrationTest`. This is a code and test audit. It is not a penetration test and it does not validate the thresholds against real data.

## Matrix

| Rule | Requirement (03) | Decision logic as implemented | Severity | Tests | Defects found and fixed | Residual limitation |
|---|---|---|---|---|---|---|
| EV-01 `DuplicateEvidenceHashRule` | Same file hash on a different milestone | Only a well-formed 64-hex hash takes part (case-insensitive). Earlier delivered rows with the same hash on another milestone and another evidence id are counted, regardless of `occurredAt` | MEDIUM same campaign, HIGH other campaign | `ev01SameMilestoneIsQuiet...`, `ev01IgnoresMissingHash...`, `ev01FlagsExactlyOneOfTwoDuplicatesInEitherDeliveryOrder`, `ev01BoundsTheListedIdentifiers...`, `onlyWellFormedSha256Hashes...`, integration redelivery and out-of-order tests | Listed identifier facts were unbounded (finding size grew with every duplicate): now at most 20 ids plus an exact `earlierEvidenceCount`. Malformed or oversized hashes were accepted into the projection and the finding: now ignored. Unsafe identifiers rejected | When two duplicates arrive in reverse time order the finding names the logically earlier submission. Exactly one finding is produced either way |
| EV-02 `FinancialEvidenceWithoutHashRule` | Receipt or invoice without a hash | `RECEIPT` or `INVOICE` (exact upper case) and no usable hash. A blank or malformed hash counts as missing | LOW | `ev02OnlyReceiptsAndInvoicesWithoutHashAreFlagged`, wrong-type sweep | **NullPointerException when `evidenceType` was absent** (`Set.of().contains(null)`); the engine swallowed it, so the event produced no finding and an ERROR log. Fixed. A malformed hash was previously treated as present and covered by neither EV-01 nor EV-02: fixed | Lower-case `invoice` is not flagged; the contract defines upper case |
| DB-01 `MinimalEvidenceApprovalRule` | Large approval on minimum evidence | `amount >= threshold` and `0 <= acceptedEvidenceCount <= minimal-evidence-count` | MEDIUM | `db01FiresExactlyAtTheThreshold...`, `db01MalformedOrMissingInputs...`, `hugeExponentAmounts...` | `new BigDecimal("1e999999999")` was accepted and `toPlainString()` would then have built a roughly 1 GB string. Amounts now follow the contract shape (at most 18 integer digits, at most 8 decimals, plain notation); anything else is ignored. Currency was echoed verbatim into text: now only upper-case tokens | Absolute amounts only; relative thresholds need a backend contract change |
| DB-02 `RapidResubmissionRule` | Resubmission soon after rejection | A request with a rejection on the same milestone within `resubmission-window` before it, both window edges inclusive. A rejection delivered after such a request now flags that request (once, same `findingId`) unless another rejection already covered it | MEDIUM | `db02WindowBoundaryIsInclusive...`, `db02FlagsAResubmissionExactlyOnceInEitherDeliveryOrder`, `db02LateRejectionIgnores...`, integration test | The reverse-delivery false negative (found by this audit, fixed 2026-10-30). `rejectedRequestId` fact now sanitised | In the reverse case the finding's source event and observation time are those of the rejection, not the request |
| DB-03 `RepeatedRequestsRule` | Many requests per milestone | Earlier delivered requests on the milestone plus this one `>= max-requests-per-milestone`, regardless of timestamps | LOW | `db03CountsEveryDeliveredRequest...`, `duplicateHashAndRepeatedRequestsAreFlaggedEvenWhenDeliveredOutOfOrder` | The previous time filter could miss the finding entirely when the oldest event was delivered last. The count-only version is correct for a count rule; verified, not just accepted | Fires on every request at or above the limit; the stable `findingId` makes the backend count them as occurrences of one finding |
| LG-01 `ReconciliationInconsistencyRule` | Reconciliation inconsistent or failed | `runStatus` exactly `INCONSISTENT` (CRITICAL) or `FAILED` (HIGH) and a valid `runId` | CRITICAL or HIGH | `lg01StatusDecidesSeverity...` | `runCode` was free text copied into a fact: now restricted to a safe token | Status match is case-sensitive by contract |
| AO-01 `ManualAdjustmentRule` | Manual escrow adjustment | Every applied adjustment with a valid amount; `amount >= adjustment-review-amount` is MEDIUM, otherwise INFO | MEDIUM or INFO | `ao01SeverityBoundary...`, `ao01ExplanationNever...`, `untrustedTextNeverReaches...` | Explanations contained the literal word `null` when `direction` or `currency` was missing. `direction` and `currency` were copied verbatim into explanations and facts (an injection and rendering vector): now only upper-case tokens, else `unspecified` | None |
| DP-01 `MisuseDisputeAfterReleaseRule` | Misuse dispute after funds released | Dispute type exactly `MISUSE_OF_FUNDS` and at least one release on the milestone at or before the dispute time | HIGH | `dp01RequiresAnEarlierRelease...`, integration test | None | **Update 2026-10-30 (implemented, not verified by execution): a release delivered after the dispute is now detected through `rise_dispute_events`; the paragraph below describes the earlier state.** **A release delivered after the dispute event is not detected.** Impact: a HIGH finding is silently missed when the monitor receives the dispute before the release it follows, which needs the relay to deliver two different aggregates out of time order (for example a monitor outage that delays only the release). Disputes are not in the projection, so the rule cannot look back when the release arrives. A fix needs a new `rise_dispute_events` table, a Flyway V2 migration, recording, retention purge and tests; not done because it changes the persisted schema of an unapproved design. Simulated releases count |

## Cross-cutting findings

| Area | Finding | Action |
|---|---|---|
| Identifier safety | The backend accepts `subject.id` only as `[A-Za-z0-9._:-]{1,80}` and dead-letters the whole event otherwise. The monitor did not check, so one malformed id in a payload could turn into a permanently FAILED outbox row | All rules now ignore ids outside that pattern (`RuleSupport.validId`) |
| Rule failure | `RiseFindingEngine` catches a rule exception, logs it and still marks the event processed, so the finding for that event is lost and the response still reads COMPLETED | Not changed. The concrete trigger (EV-02 on a missing type) is fixed, and a sweep test now feeds hostile JSON types to every rule. The behaviour is deliberate (one rule must not block the others) but means a future rule bug is silent apart from an ERROR log |
| Determinism | `findingId` is a SHA-256 of rule, subject and discriminator | Verified by test: evaluating the same envelope twice yields the same id |
| AI isolation | Rules never read `aiNote`; notes are attached after evaluation in a separate field (`FindingNoteTest`) | Unchanged |
| Output contract | Every finding returned by all eight rules validates against `contracts/findings/finding.v1.schema.json` | Asserted in `RiseMonitoringIntegrationTest.findingTextsAvoidAccusatoryLanguage` |

## Not covered

- No concurrency stress beyond the existing eight-thread test (`concurrentIdenticalRequestsProduceOneAnalysis...`).
- No mutation testing: the regression tests for the huge-exponent amount, the bounded id lists and the log capture were not shown to fail against the old code by reverting it. The EV-02 null-type and AO-01 `null` text defects were found by these tests failing first; the enum-like injection gap in AO-01 was found by the AI evaluation, not by a test.
- Thresholds are placeholders. The audit says nothing about whether 50,000,000 or 3 are the right numbers.
